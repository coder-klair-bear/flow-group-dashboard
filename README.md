# Flow Group AB — Annonspanel

Advertising dashboard for Flow Group's two apps, **Sveapanelen** (Sweden) and
**Rewly** (NO, DK, FI, NL, FR, DE), across TikTok, Meta, Google, Snapchat and —
eventually — Unity.

React + Vite on the front, Express + Drizzle + PostgreSQL behind it, TypeScript
throughout.

---

## What is real and what is sample

This distinction is the point of the whole project, so it is enforced in the
data model rather than left to the UI.

| Real, from the two publish trackers | Sample, generated by the seed         |
| ----------------------------------- | ------------------------------------- |
| All 41 creatives, names and ids     | Spend, installs, clicks, impressions  |
| Drive links and link types          | Publish dates                         |
| Countries per creative              | Campaign and ad set names             |
| Per-platform status (Ja/Nej/Bara ios/Rejected) | Ad account ids and names   |
| Sheet notes, both languages         | What each platform reports back       |
| Coverage, gaps, rejections, duplicates | Inactive ads, high-cost alerts     |

Every sample figure carries a dotted purple underline in the UI, and every card
that shows sample data carries an "Exempeldata" chip. `daily_metrics.is_sample`
and `ad_accounts.is_sample` mark it in the database too, so when a platform is
connected in stage 5 its rows simply replace that platform's sample rows.
Sample and live are never mixed inside one number.

## Getting it running

Requires **Node 20.11+** and a **PostgreSQL 14+** database.

```bash
cp .env.example .env          # then point DATABASE_URL at your database
npm install
npm run db:push               # create the schema
npm run db:seed               # load the sheets + generate sample metrics
npm run dev                   # API on :4000, web on :5173
```

Open http://localhost:5173.

The Vite dev server proxies `/api` to the Express process, so the two share an
origin in development exactly as they do in production.

### Other commands

| Command               | What it does                                                     |
| --------------------- | ---------------------------------------------------------------- |
| `npm run db:generate` | Write SQL migration files to `server/drizzle/`                    |
| `npm run db:migrate`  | Apply those migration files                                       |
| `npm run db:push`     | Push the schema straight to the database (fastest for development) |
| `npm run db:reset`    | Push, then reseed from scratch                                     |
| `npm run db:studio`   | Drizzle Studio, to browse the tables                               |
| `npm run typecheck`   | Typecheck both workspaces                                          |
| `npm run build`       | Build both; the API then serves `web/dist` from the same origin    |
| `npm start`           | Run the built server                                               |

No migration files are checked in yet — `db:push` is the quickest way to a
working database. Run `db:generate` once the schema settles and you want a
migration history.

## Layout

```
flow-group-dashboard/
├─ server/
│  ├─ drizzle.config.ts
│  └─ src/
│     ├─ index.ts                  Express app; serves web/dist in production
│     ├─ env.ts                    .env loading, read from the repo root
│     ├─ db/
│     │  ├─ schema.ts              Drizzle schema — the whole data model
│     │  ├─ source-data.ts         REAL: the two sheets, transcribed
│     │  ├─ sample.ts              SAMPLE: the deterministic generator
│     │  ├─ seed.ts                Loads both into PostgreSQL
│     │  └─ client.ts, migrate.ts
│     ├─ services/
│     │  ├─ catalog.ts             Cached read of the sheet-derived catalogue
│     │  ├─ filters.ts             Query parsing, date ranges, previous period
│     │  ├─ performance.ts         All metric aggregation, in SQL
│     │  ├─ publishing.ts          Coverage, gaps, duplicates, name matching
│     │  └─ alerts.ts              "Needs your attention"
│     ├─ routes/                   One router per view
│     └─ shared/types.ts           The API contract, types only
└─ web/
   └─ src/
      ├─ views/                    Overview, Creatives, Performance, Top,
      │                            Unpublished, Publishing, Integrations
      ├─ components/               Shell, filter bar, charts, cards, icons
      ├─ state/                    Meta (catalogue), store (UI state), params
      ├─ i18n/                     Swedish and English, every string
      ├─ lib/                      Fetch hook, formatting, labels
      └─ styles/global.css         The design, ported from the prototype
```

`web` imports `server/src/shared/types.ts` through the `@shared` alias. It
contains types only, so nothing from the server reaches the browser bundle —
the alias exists to keep one definition of the API contract rather than two.

## Data model

```
apps ─┬─ creatives ─┬─ creative_countries ── countries
      │             └─ creative_statuses ──── platforms
      ├─ ad_accounts ───────────────────────── platforms
      └─ placements ── daily_metrics
```

A **placement** is one creative × platform × country — the grain the ad
platforms actually report on. Every row of `daily_metrics` hangs off a
placement, so every number knows its app, country, platform, campaign, ad
account and creative without a single denormalised column. That is the lineage
the Integrations view promises.

Placements exist only for the four platforms that have a column in the sheets.
Unity deliberately has none: inventing rows for it would hide the gap the
dashboard is meant to show.

### Splitting by iOS and Android

The sheets only record an operating system where someone wrote it out ("Bara
ios", "only ios"). Everything else is assumed to run on both. So `placements`
carries an `ios_share`, and an OS breakdown weights the same delivery rows by
that share rather than reading a real OS column. Every view that shows an OS
split says so in a note underneath.

## API

All endpoints take the same filter parameters: `app`, `country`, `platform`,
`campaign`, `creative`, `os`, `status`, `q`, `from`, `to`, `pubFrom`, `pubTo`.

| Endpoint            | Returns                                                       |
| ------------------- | ------------------------------------------------------------- |
| `GET /api/meta`     | Apps, countries, platforms, all creatives, campaigns, today    |
| `GET /api/overview` | Fixed periods, range totals vs previous, spark, coverage, alerts |
| `GET /api/creatives`| Matching creatives and placements                              |
| `GET /api/performance` | Totals, time series (`gran`), breakdown (`dim`)             |
| `GET /api/top`      | Ranked creatives (`rank`), weakest, best per `dim`             |
| `GET /api/publishing` | Matrix, live placements, gaps, rejections, mismatches, duplicates |
| `GET /api/unpublished` | Out nowhere, partly out, Android missing                    |
| `GET /api/integrations` | Source status and the accounts behind each               |
| `POST /api/refresh` | Drops the server's catalogue cache                             |

Series buckets come back as ISO dates rather than formatted labels, and alerts
carry both languages, so switching between Swedish and English never needs a
round trip.

## Design decisions worth knowing

**Cost per install needs volume.** Ranking by CPI ignores creatives under 8
installs — one lucky install would otherwise top the chart at 4 kr.

**Duplicates are app- and market-specific.** "Vad hade du gjort för 100kr"
exists for both DK and FI; that is localisation, not duplication. Two creatives
count as duplicates only when they are the same idea in the same app *and*
share a market. The same idea across markets is listed separately, as shared
concepts.

**Nothing is ever paused automatically.** The dashboard reports; every change
to a campaign is made by a person.

**The seed is deterministic.** `SEED_SALT` drives a seeded PRNG, so re-running
the seed rebuilds an identical dataset. Change the salt in `.env` for a
different-looking demo.
